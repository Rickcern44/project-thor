## Context

The league runs today on a hand-edited shared spreadsheet covering sign-ups, waitlists, and dues. The pain points are concurrent edits, missed waitlist openings, and balances drifting out of sync. This app replaces the spreadsheet as the source of truth. The user base is a closed, known group (a rec league), which unlocks simpler choices than a public product would allow — notably admin-invite-only accounts.

A guiding principle emerged during exploration and shapes nearly every decision below:

> **The app keeps state correct automatically; the admin makes the human judgment calls.**

Nothing critical is automated away from the person who should own it (who gets promoted off the waitlist, who was a no-show, who paid), and nothing manual is required for the app to stay in a correct state.

## Goals / Non-Goals

**Goals:**
- Single source of truth for sign-ups, waitlists, and per-game dues.
- Frictionless courtside sign-up/cancel on a phone.
- Fast per-game admin reconciliation (settle up, waive no-shows).
- Installable PWA experience with best-effort push.
- Clean one-time migration off the spreadsheet.

**Non-Goals (v1):**
- No online payment processing — dues are recorded manually by an admin.
- No automated waitlist promotion — admin decides.
- No team-balancing / skill ratings — a game is just a roster of attendees.
- No recurring-series editing (edit-all-Tuesdays); game instances are independent.
- No two-way spreadsheet sync — the sheet is imported once, then retired.
- No native mobile apps.
- No blocking of sign-ups based on outstanding balances.

## Decisions

### D1. Spreadsheet is a one-time import, not a sync
Import the sheet once; the app becomes authoritative and the sheet retires. **Why:** the sheet only exists because there was no app — there is no downstream tool or second editor that must keep reading it. This removes the hardest problem in the space (two-way sync / conflict resolution) entirely. *Alternatives considered:* read-only mirror (doesn't let the app own state); app-authoritative-with-push-to-sheet (keeps a sheet nobody needs); true two-way sync (rejected — heavy conflict machinery for no benefit).

### D2. Admin-invite-only accounts (no open registration)
Admins import the roster, then invite each player; the invite links to their imported record. **Why:** for a closed group this makes identity linking automatic and sidesteps the "is this new signup the same John Smith who owes $40?" matching problem. *Alternatives:* open registration + admin reconciliation (creates duplicate/merge busywork); fresh accounts with manually keyed balances (loses history, more onboarding data entry).

### D3. Per-game fee, flat amount, same every game
A single configurable fee applies to every game. **Why:** matches how the league actually charges (per night of play) and keeps the ledger simple. Per-game override was considered but the league confirmed the fee is uniform; a default-with-override pattern is used for **capacity** but not fee.

### D4. Charge lifecycle: on sign-up → erase on cancel → owed at game time → admin waive post-game
The charge attaches when a player signs up, is erased with no penalty if they cancel, and stands if they're on the roster at game time. After the game the admin can remove the charge for anyone who was rostered but didn't show. **Why:** the roster at game time is a correct-by-default attendance list, so the charge *is* the attendance record — no separate attendance feature needed. The admin's post-game job is only to *subtract* no-shows. This also resolves the late-cancel/waitlist interaction cleanly: a canceller's charge is erased and their replacement (now rostered) owes — one spot, one charge, no double-billing. *Alternatives:* owe-only-if-marked-present (more admin data entry every game); hard cancel-cutoff penalty (rejected — league doesn't want to penalize cancels).

### D5. Balances are tracked but never block sign-up
Outstanding balances are informational; admins chase them out-of-band. **Why:** the league explicitly does not want the app to police money by locking players out. *Alternatives:* hard block on unpaid balance; warn-but-allow — both rejected as heavier-handed than the league wants.

### D6. Single live game, auto-generated by time, opened by a configurable lead time
A recurring template stores day/time/capacity/fee defaults; the next game materializes automatically from it. Ad-hoc one-off games can also be created. **Why:** "next game only" collapses the notorious recurring-series-editing problem to nothing (a series of length one has nothing to edit across). Time-based generation keeps it hands-off, and because charges are correct-by-default, the just-finished game does not need to be reconciled *before* the next opens — it simply drops into a "past games awaiting reconciliation" list. *Alternatives:* whole-season-up-front (visibility, but edit churn and series-exception complexity); rolling window (middle ground, still multiple live instances); admin-closes-out-to-advance (nice rhythm, but the league preferred fully automatic).

**Sign-up window (refines the "opens at previous tip-off" idea):** sign-ups do NOT open the instant the previous game ends. Instead a game opens for sign-up at `start_time − signup_lead_time`, where `signup_lead_time` is a **configurable template setting (default: 1 day)**. This decouples "game exists" from "game is open," giving a game three states:

```
materialized (closed) ──▶ open for sign-up ──▶ past / awaiting reconciliation
                         (at start − lead)      (once start_time passes)
```

Between a game finishing and the next opening there is an intentional **quiet gap** (no game open) — a natural cooldown. **Constraint:** `signup_lead_time` MUST be shorter than the interval between games, or two games would be open at once, breaking the single-live-game invariant. The app validates this. *Alternatives:* open at previous tip-off (the original model — max notice but week-old availability, and no quiet gap); admin-opens-manually (rejected — re-introduces a manual step).

### D7. Instances are independent (no recurring-series machinery)
The template is a *generator*, not a live link. Editing, skipping, or cancelling a game touches only that instance. **Why:** avoids the Google-Calendar "this event vs. the series" rabbit hole; combined with D6 (one live game) there is never more than one instance to reason about anyway.

### D8. Installable PWA
Responsive web app installable to the home screen. **Why:** one codebase covers courtside phone sign-ups and laptop admin reconciliation; no app-store cycles. *Alternatives:* native (app-store overhead, main perk is push — see D9); plain responsive web (fine, but the installable icon is a cheap UX win).

### D9. In-app notification list as baseline + PWA push on top
Every notification lands in an in-app list; PWA push is a best-effort layer on top for waitlist promotion and new-game events. **Why:** PWA Web Push works well on Android/desktop but on iOS only fires if the user has installed the PWA to their home screen — a coverage gap the app can't control. Layering push over a reliable in-app list means the un-installed iPhone player still sees the notification next time they open the app. *Alternatives:* in-app only (nothing proactively reaches anyone); email (reaches everyone, but adds a sending service and the league preferred push); SMS (vendor + per-message cost).

### D10. Passwordless magic-link authentication
Invited players activate and log in via an emailed magic link; there are no passwords. **Why:** lowest friction for a casual rec-league audience, and it removes password storage, reset flows, and forgotten-password support entirely. It also composes cleanly with D2 (admin-invite-only): the invite *is* the first magic link. *Alternatives:* set-a-password (familiar but adds reset/support surface); magic-link-plus-optional-password (more flexible, more to build — deferred).

### D11. Contact fields: email and phone both required
Every player record requires both an email and a phone number. **Why:** email is the delivery channel for magic-link auth (D10) and notifications; the league chose to also make phone mandatory so an admin can always reach a player directly to chase dues. **Consequence for import:** any imported row missing either field is flagged for admin review (per the roster-import validation rule) rather than imported incomplete — so if the current spreadsheet lacks phone numbers, expect a batch of rows to need attention at import time. *Alternatives:* email-only-required (smoother import, weaker reachability); either-email-or-phone (flexible for patchy data, but breaks email-based magic-link delivery for phone-only players).

## Risks / Trade-offs

- **iOS push coverage gap** → Mitigated by D9 (in-app list is the guaranteed baseline) and an onboarding nudge to "Add to Home Screen → enable alerts."
- **Time-based next-game generation can outrun reconciliation** (a new game opens while the last is unsettled) → Mitigated because charges are correct-by-default (D4); a "past games awaiting reconciliation" view keeps no-show waivers from being forgotten.
- **Admin-decided waitlist promotion + in-app-first notifications** means the waitlist moves at "whenever the admin looks / gets the push" speed → Acceptable for a league organizer; email-to-admin is the natural future upgrade if it feels slow.
- **Spreadsheet import data quality** (missing emails, inconsistent names) → Import should validate and surface unmatched/ambiguous rows for admin review rather than silently dropping them.
- **Balances never block play (D5)** means uncollected dues can accumulate → Accepted by design; the app surfaces balances prominently so admins can chase them.

## Migration Plan

1. Stand up the app with schema and auth; no players yet.
2. Run the one-time spreadsheet importer into a staging state; admin reviews unmatched/ambiguous rows.
3. Admin invites players; invites link to imported records (D2).
4. Verify balances and roster against the sheet.
5. Announce cutover; spreadsheet becomes read-only/archived and is no longer authoritative.
- **Rollback:** until cutover is announced, the spreadsheet remains the source of truth; the app can be discarded with no data loss since import is one-directional.

## Resolved Questions

- **Sign-up open timing** → Configurable `signup_lead_time` per template, default 1 day; game opens at `start − lead`. Must be shorter than the inter-game interval. (See D6.)
- **Required contact fields** → Email and phone both required. (See D11.)
- **Invite auth mechanism** → Passwordless magic link. (See D10.)
